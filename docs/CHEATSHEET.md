# Stacker CLI cheatsheet

Every command here exists in the CLI as of 0.3.10 - the list came from
`--help` and the argument definitions, not from memory. Things that bite are
marked **trap** with the entry in [BUGS.md](../BUGS.md) that describes them.

Schema of `stacker.yml`: [STACKER_YML_REFERENCE.md](STACKER_YML_REFERENCE.md).

## Install and identity

```
brew install trydirect/tap/stacker        # or: curl -fsSL https://get.stacker.my/install.sh | bash
stacker --version
stacker update                            # self-update
stacker login                             # the session expires; check before a long session
stacker whoami                            # login, API, plan
```

## A project from nothing

```
stacker init --app-type node              # static | node | python | rust | go | php
stacker init --with-ai --ai-provider anthropic --ai-model claude-sonnet-4-20250514
stacker init -g owner/repo                # generate from a GitHub repository
stacker config validate
stacker config show --resolved            # what the config means after defaults
stacker config fix                        # repair what it can
stacker config example                    # a reference stacker.yml
```

Add services from templates:

```
stacker service add postgres              # omit the name for an interactive picker
stacker service import redis --from-compose ./docker-compose.yml
stacker service list
stacker service remove postgres
```

> **Trap (#47):** after `service add`, `config validate` fails with
> `Environment variable not found: $POSTGRES_PASSWORD` even though the command
> just wrote that password into `.env`. Nothing adds the `env_file:` line that
> lets the validator see it:
>
> ```
> echo 'env_file: .env' >> stacker.yml
> ```

> **CMD follows `package.json` (#49 fixed):** for `--app-type node` the
> generated Dockerfile runs `npm start` when `scripts.start` exists, else
> `node <package.json main>`, else `server.js`. No renaming needed.

## Secrets

```
stacker secrets set KEY=value                      # local .env
stacker secrets list                               # values masked
stacker secrets list --show
stacker secrets get KEY --show
stacker secrets validate                           # every ${VAR} in the config is set
stacker secrets delete KEY

stacker secrets apps                               # deployable targets for remote secrets
stacker secrets set NAME --scope service --service <target> --body "value"
stacker secrets set NAME --scope server --server-id <id> --body-file ./file
stacker secrets push --service <target>            # push local .env to the remote store
```

Reserved prefixes, rejected: `STACKER_`, `DOCKER_`, `VAULT_`, `AGENT_`.

## Run it here

```
stacker target local                      # local | cloud | server
stacker deploy --target local
stacker deploy --target local --force-rebuild
stacker logs --service app --tail 50
stacker destroy -y                        # add --volumes to drop named volumes
```

A port already taken on the host stops the deploy before it breaks anything,
and names the port.

## Deploy to a server

```
stacker deploy --target server --server-host <ip> --server-ssh-key ~/.ssh/id_rsa
stacker deploy --target cloud --key <saved-credential>      # provision a new server
stacker deploy --target cloud --server <saved-server>       # reuse a saved one
stacker deploy --plan                     # read-only plan
stacker deploy --dry-run
stacker deploy <service>                  # surgical: one service, others untouched
stacker deploy --lock                     # write server details back into stacker.yml
```

> **Trap (#48):** a project generated by `init` builds its image locally, and
> **no remote target builds images**. Publish the image and point at it:
>
> ```
> docker build -t <ns>/<app>:1 . && docker push <ns>/<app>:1
> # app:
> #   image: <ns>/<app>:1
> ```
>
> `--dry-run` currently passes configs that the real deploy rejects, so a green
> preview is not a promise.

Cloud bookkeeping:

```
stacker clouds                            # saved provider credentials
stacker servers
stacker projects
stacker deployments                       # newest first - this is where hashes come from
stacker ssh-key generate | show | upload | inject
```

## Which deployment am I talking to

One project can hold several deployments - one saved context per target. Since
0.3.10 every command that resolves one implicitly says so:

```
ℹ resolved deployment deployment_… (from .stacker/deployment-server.lock, target: server)
```

```
stacker deployment use <hash>             # pin it in stacker.yml  (0.3.10+)
stacker deployment use --clear            # unpin
stacker <command> --deployment <hash>     # one-off, overrides everything
```

Resolution order: `--deployment`, then the pin, then the active target's lock,
then the newest lock. If a newer lock exists than the one chosen, the command
warns with both dates (#55).

```
stacker deployment state                  # status, runtime, agent, remote paths
stacker deployment events                 # structured progress of a deployment
stacker connect --handoff <token>         # attach this directory to a dashboard deployment
stacker pull                              # pull project configuration down
stacker sync --verify                     # push project configuration up, without deploying
stacker resolve                           # force-complete a stuck paused/error deployment
```

> **Trap (#54):** `sync` reports success even with no compose file present, and
> it does not update the stored compose - only a full deploy does.

## Watch it without SSH

```
stacker agent status                      # agent, heartbeat, apps, containers - one screen
stacker agent health                      # per container: state, CPU%, MEM%, image
stacker agent health --system
stacker agent apps
stacker agent containers
stacker agent history                     # what the agent has been asked to do
stacker agent logs <app> --limit 200
stacker logs --service <app> --tail 50
stacker status                            # see the trap below
```

Every `agent` command takes `--deployment <hash>` and `--json`.

```
stacker monitor --once                    # one check, cron-friendly
stacker monitor --interval 30             # loop
```

`monitor` needs an alerts block; the key is `target:`, not what the error
message says (#54):

```yaml
monitoring:
  alerts:
    interval: 30
    on_recovery: true
    target:
      terminal: true        # or url: https://…  for a webhook
```

> **Trap (#20, #25):** `stacker status` can resolve the wrong project and show
> a deployment from a server that no longer exists. Use `deployment state` and
> `agent status`.

> **Trap (#53):** the remote compose path printed by `deployment state` and
> `explain topology` is not always the directory docker is using. The truth:
> `docker inspect <container> --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'`.

## Ship a new version

```
stacker agent deploy-app <app> --image <ns>/<app>:2 --force
stacker agent deploy-app <app> --plan                  # preview, then --apply-plan <file>
stacker agent restart <app> --force
stacker agent remove-app <app> --volumes --remove-image
stacker service deploy <name>                          # deploy one declared service
stacker rollback --version <template-version> -y       # marketplace deployments
stacker deployment rollback --to <ref> --plan
```

Measured on a small stack: the command returns in about 13 s and the app
answers again about 6 s later.

## Proxy, domains, firewall

```
stacker proxy detect                      # what is actually in front
stacker proxy add                         # see the trap
stacker agent configure-proxy <app> --domain app.example.com --port 3000 --no-ssl
stacker agent configure-firewall --public-ports 8080/tcp --persist
stacker cloud firewall list
stacker cloud firewall add --public-ports 5000/tcp --dry-run
stacker cloud firewall remove --public-ports 5000/tcp
```

`cloud firewall` opens the provider's firewall - without it only SSH is
reachable, whatever the container publishes. `--dry-run` shows the change
first, and `--server-id <id>` targets a server other than the resolved one.

> **Trap (#37, #38):** `proxy add` rewrites the whole `stacker.yml` and drops
> every comment, and on a fresh server its remote half needs a credential read
> that is not there yet.

> In `proxy.domains[].upstream` write a bare `service:port`. With a scheme it
> becomes `http://http://…` and answers 500 (#43), and a redeploy does not
> rewrite an entry that already exists (#44).

## Marketplace

```
stacker find <query>
stacker templates                         # aliases: catalog, apps
stacker install <template>                # see the trap
stacker submit --version 1.0.0 --slug my-app --price 0
stacker marketplace status
stacker marketplace logs
```

> **Trap (#12, #30, #33):** `install` writes only `stacker.yml` - no `scripts/`,
> no `.env` - and the catalogue can serve a template older than the
> repository.

## Pipes, CI, AI

```
stacker pipe scan | create | diff | apply | list | trigger | history | replay
stacker ci export --platform github          # a pipeline for your CI
stacker ci validate --platform github
stacker ai ask "why is my container crashing?" --context ./logs.txt
stacker ai                                   # interactive, add --write to let it edit
stacker explain topology                     # local files next to the remote ones
stacker explain env <app>
stacker completion zsh                       # shell completion
```

## The short version

```
stacker init --app-type node && echo 'env_file: .env' >> stacker.yml
stacker config validate
stacker deploy --target local                       # it runs here
docker build -t <ns>/app:1 . && docker push <ns>/app:1
stacker deploy --target server --server-host <ip> --server-ssh-key <key>
stacker deployments | head -3                       # take the hash
stacker deployment use <hash>
stacker agent status
stacker agent deploy-app app --image <ns>/app:2 --force
```
